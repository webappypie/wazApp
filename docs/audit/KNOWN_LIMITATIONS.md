# Known Limitations & Blockers — Phase 0

## Environment
- E1. Host is Windows 11: **no Xcode / macOS** → iOS build, archive, Photos/Files/share-sheet and TestFlight validation are *blocked-by-environment*. iOS code can be written but cannot be claimed verified.
- E2. `flutter doctor`: Android SDK 36.1.0 present, but **Android licenses not accepted** (`flutter doctor --android-licenses` needs interactive acceptance by the owner). May block Gradle SDK component download.
- E3. Visual Studio missing → no Windows desktop target (not needed).
- E4. `flutter devices` lists one physical Android device (`2201116SI`, Android 13 / API 33, arm64) plus Windows/Chrome/Edge. Only API 33 is available: Android 11/12/14+ behaviour (SAF `Android/media`, partial photo access) cannot be covered. No physical-device result is claimed anywhere in these reports.

## Owner-supplied items missing (blockers, nothing fabricated)
- B1. `wap_core_sdk`, `wap_ads_sdk`, `wap_notifications_sdk`, `wap_promo_sdk`: not published on pub.dev, not in repo. Need git URL / private pub registry / local path + docs for their public API (the guide only shows `WapCore.initialize`, `WapAds.initialize`, `WapNotifications.initialize`, `ServiceControlGuard`).
- B2. iOS `GoogleService-Info.plist` and Android `google-services.json` are in the repo root; guide §3 places them in `android/app/` and `ios/Runner/`. `ios/` does not exist yet. Placement is mechanical once D1 is decided.
- B3. Play Billing **product ID for one-time Remove Ads** not supplied; Play Console app/product + licence-tester account needed for sandbox tests. App Store IAP product ID likewise.
- B4. Response schemas for ads config / notifications register / feed not in the guide (see ARCHITECTURE_FINDINGS conflicts).
- B5. Release keystore (`android/key.properties`) not supplied; upload key must come from owner. Not generated by the agent.
- B6. Trademark / store-name / domain clearance for "WazApp" (resembles "WhatsApp") is an owner/legal action; README already flags it.
- B7. AdMob production App ID must be placed in the release manifest by owner confirmation (guide conflict #2); `app-ads.txt` hosting is an owner action.

## Product/platform limits to state honestly in-app
- Android status access depends on OS version/OEM; Android 11+ restricts selecting `Android/media` through the system folder picker on some builds. Must be validated per device, WhatsApp and WhatsApp Business separately.
- iOS cannot read WhatsApp's status storage; only Photos/Files import.
- Private Folder = app-private storage + optional device authentication. **Not encryption** unless later implemented and tested; data is lost on uninstall.

## Phase 1 additions
- E5. **Device install blocked:** `adb install` to the attached Xiaomi (`2201116SI`, Android 13) failed with `INSTALL_FAILED_USER_RESTRICTED`. Owner action: Settings > Additional settings > Developer options > enable **Install via USB** (and "USB debugging (Security settings)"), then re-run `flutter install`. Until then the native SAF bridge (`StatusAccessHandler.kt`) is compiled (debug build OK) but **not exercised on a device**.
- E6. The attached phone has WhatsApp Business installed and its `.Statuses` folder currently holds no status files (only `.nomedia`); end-to-end saving needs the owner to view a status first. Plain WhatsApp is not installed on it (WhatsApp vs Business separation can only be unit-tested).
- L1. Status access depends on the OS picker honouring the initial-folder hint and allowing `Android/media`; validated on no device yet.
- L2. iOS: scaffold only, nothing built or run; Photos/Files import, share and thumbnail behaviour unverified; no gallery export on iOS (Share used).
- L3. "Save to gallery" requires Android 10+ (MediaStore RELATIVE_PATH); on 8-9 the app says to use Share.
- L4. Saved media is app-private and lost on uninstall (stated in Settings); it is not encrypted and is never described as encrypted.
- L5. Widget tests on Windows cannot assert file unlink after image decode (open handles); the test asserts the DB/file consistency invariant on every OS and full deletion on POSIX only.

## Phase 2 additions
- L6. Editor/status maker are verified with automated tests only; no screenshot or touch test on a device/emulator exists yet (E5 still blocks install; a second install attempt after Phase 2 failed identically).
- L7. Overlays (text/stickers) stay fixed in the frame when the photo is rotated or flipped, and rotate/flip reset the crop. Cropping keeps overlays at the same spot on the photo.
- L8. Export is bounded to 4096 px on the long side and always JPEG q92 without EXIF; there is no quality/format choice.
- L9. JPEG encoding is pure Dart in a background isolate: cancellation takes effect between stages, not inside the encode; slow on low-end devices (not measured).
- L10. Status maker exports 9:16 only; maximum 300 characters; emoji depend on the platform emoji font.
- L11. No sharpness control (not implementable honestly without native/shader code); video editing, Private Folder, Storage Manager are still missing (Phases 3-4).

## Not yet verified (nothing has been verified on a device in this audit)
All runtime behaviour; only static analysis and unit/widget tests were run on the host (see `BASELINE_AUDIT.md`).
