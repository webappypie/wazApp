# Known Limitations & Blockers — Phase 0

## Environment
- E1. Host is Windows 11: **no Xcode / macOS** → iOS build, archive, Photos/Files/share-sheet and TestFlight validation are *blocked-by-environment*. iOS code can be written but cannot be claimed verified.
- E2. `flutter doctor`: Android SDK 36.1.0 present, but **Android licenses not accepted** (`flutter doctor --android-licenses` needs interactive acceptance by the owner). May block Gradle SDK component download.
- E3. Visual Studio missing → no Windows desktop target (not needed).
- E4. `flutter devices` lists one physical Android device (`2201116SI`, Android 13 / API 33, arm64) plus Windows/Chrome/Edge. Only API 33 is available: Android 11/12/14+ behaviour (SAF `Android/media`, partial photo access) cannot be covered. No physical-device result is claimed anywhere in these reports.

## Owner-supplied items missing (blockers, nothing fabricated)
- B1. `wap_core_sdk`, `wap_ads_sdk`, `wap_notifications_sdk`, `wap_promo_sdk`: not published on pub.dev, not in repo. Need git URL / private pub registry / local path + docs for their public API (the guide only shows `WapCore.initialize`, `WapAds.initialize`, `WapNotifications.initialize`, `ServiceControlGuard`).
- B2. iOS `GoogleService-Info.plist` and Android `google-services.json` are in the repo root; guide §3 places them in `android/app/` and `ios/Runner/`. `ios/` does not exist yet. Placement is mechanical once D1 is decided.
- B3. Play Billing **product ID for one-time Remove Ads** not supplied; Play Console app/product + licence-tester account needed for sandbox tests. App Store IAP product ID likewise.
- B4. Response schemas for ads config / notifications register / feed not in the guide (see ARCHITECTURE_FINDINGS conflicts).
- B5. Release keystore (`android/key.properties`) not supplied; upload key must come from owner. Not generated by the agent.
- B6. Trademark / store-name / domain clearance for "WazApp" (resembles "WhatsApp") is an owner/legal action; README already flags it.
- B7. AdMob production App ID must be placed in the release manifest by owner confirmation (guide conflict #2); `app-ads.txt` hosting is an owner action.

## Product/platform limits to state honestly in-app
- Android status access depends on OS version/OEM; Android 11+ restricts selecting `Android/media` through the system folder picker on some builds. Must be validated per device, WhatsApp and WhatsApp Business separately.
- iOS cannot read WhatsApp's status storage; only Photos/Files import.
- Private Folder = app-private storage + optional device authentication. **Not encryption** unless later implemented and tested; data is lost on uninstall.

## Phase 1 additions
- E5. **Device install blocked:** `adb install` to the attached Xiaomi (`2201116SI`, Android 13) failed with `INSTALL_FAILED_USER_RESTRICTED`. Owner action: Settings > Additional settings > Developer options > enable **Install via USB** (and "USB debugging (Security settings)"), then re-run `flutter install`. Until then the native SAF bridge (`StatusAccessHandler.kt`) is compiled (debug build OK) but **not exercised on a device**.
- E6. The attached phone has WhatsApp Business installed and its `.Statuses` folder currently holds no status files (only `.nomedia`); end-to-end saving needs the owner to view a status first. Plain WhatsApp is not installed on it (WhatsApp vs Business separation can only be unit-tested).
- L1. Status access depends on the OS picker honouring the initial-folder hint and allowing `Android/media`; validated on no device yet.
- L2. iOS: scaffold only, nothing built or run; Photos/Files import, share and thumbnail behaviour unverified; no gallery export on iOS (Share used).
- L3. "Save to gallery" requires Android 10+ (MediaStore RELATIVE_PATH); on 8-9 the app says to use Share.
- L4. Saved media is app-private and lost on uninstall (stated in Settings); it is not encrypted and is never described as encrypted.
- L5. Widget tests on Windows cannot assert file unlink after image decode (open handles); the test asserts the DB/file consistency invariant on every OS and full deletion on POSIX only.

## Phase 2 additions
- L6. Editor/status maker are verified with automated tests only; no screenshot or touch test on a device/emulator exists yet (E5 still blocks install; a second install attempt after Phase 2 failed identically).
- L7. Overlays (text/stickers) stay fixed in the frame when the photo is rotated or flipped, and rotate/flip reset the crop. Cropping keeps overlays at the same spot on the photo.
- L8. Export is bounded to 4096 px on the long side and always JPEG q92 without EXIF; there is no quality/format choice.
- L9. JPEG encoding is pure Dart in a background isolate: cancellation takes effect between stages, not inside the encode; slow on low-end devices (not measured).
- L10. Status maker exports 9:16 only; maximum 300 characters; emoji depend on the platform emoji font.
- L11. No sharpness control (not implementable honestly without native/shader code); video editing, Private Folder, Storage Manager are still missing (Phases 3-4).

## Phase 3 additions
- L12. **iOS has no video editor** (no verified encoder; Create and the viewer menu hide it there). Implementation would use AVFoundation and needs macOS/Xcode (E1).
- L13. Video export is Android-only and was validated on an x86_64 **emulator** (software encoder); phone hardware encoders, 4K/HEVC/10-bit/HDR sources, very long videos and low-storage devices are untested.
- L14. Output is always H.264/AAC in MP4, frame-accurate trim by re-encoding (slower than stream copy, no "lossless trim"); bitrate is derived from resolution (no quality slider); no rotate/flip, speed, filters or audio replacement for video.
- L15. Export time depends on the device; progress is polled every 250 ms from the encoder. Cancelling takes effect immediately for the encoder; partial output is deleted.
- L16. Crop/trim handles are touch-driven and were exercised only with simulated gestures in widget tests.
- E7. The Android emulator and test clips generated on the host with a bundled ffmpeg (dev tool, not shipped) were used for verification; no user media was used.

## Phase 4 additions
- L17. **The Private Folder is not encrypted.** It hides items and can require device authentication; anyone with root/forensic access, a backup extractor, or an unlocked phone with the lock switched off can read the files. They are deleted on uninstall/clear data. The UI says so in three places.
- L18. The device lock is a screen gate. There is no screenshot/recents blocking (`FLAG_SECURE`) yet, and a screen recording while the folder is open would capture its contents.
- L19. Authentication was exercised on an **emulator** with a PIN (success path with PIN entry, dismissal, and no-screen-lock behaviour). Fingerprint/face prompts, OEM biometric UIs and iOS Face ID/Touch ID are untested.
- L20. If the lock is on but the phone no longer has any screen lock, the folder opens with a red "Not protected right now" banner (deliberate: never lock users out of their own files).
- L21. Private items cannot be edited (the copy would land in the normal library); sharing and "save a copy to gallery" remain explicit actions and leave a copy outside WazApp.
- L22. Storage Manager reports only WazApp's own storage (not device free space, WhatsApp, or the gallery). Look-alike detection works for photos only (videos match only when byte-identical); the 64-bit fingerprint can miss heavy edits and can occasionally group two similar photos, which is why nothing is selected for you without a click and every deletion is confirmed.
- L23. Duplicate scans hash files in a background isolate; on a very large library the first scan can take a while (hashes are cached afterwards). Not measured on a phone.
- L24. A saved status that was moved to the Private Folder still counts as "already saved" on the Home grid (prevents re-saving a second copy).

## Phase 5 additions
- L25. **Service control fails open by design** (guide section 9): offline, airplane mode, a blocked host or a deliberately dropped request all lift the notice. It cannot be enforced against a user who blocks the request.
- L26. The notice appears just after the first frame (the check does not delay launch). On a normal network that is well under a second; on a slow one the app is usable until the answer arrives.
- L27. The live endpoint is public; the platform key is **not required** for it and is not a secret once compiled into an APK. It is never in source or logs; pass it only with `--dart-define=WAP_APP_KEY=...` when ads/notifications need it.
- L28. The Android network path (INTERNET permission, external-browser launch) was verified by a release build and host tests, **not on a device or emulator**.
- L29. The live payload differs from the guide's example (`updatedAt` is `{_seconds,_nanoseconds}`, text fields absent while enabled); the parser tolerates both. If WAPCentral changes the shape again the client fails open, never blocks.
- L30. **Not implemented (blocked on the owner):** ads, push notifications and the in-app feed, promotions, Remove Ads billing. No dead buttons or placeholder UI exist for them. Details and exact owner actions: `WAPCENTRAL_INTEGRATION_STATUS.md` (B1, B3, B4, B7).

## Not yet verified (nothing has been verified on a device in this audit)
All runtime behaviour; only static analysis and unit/widget tests were run on the host (see `BASELINE_AUDIT.md`).

## Phase 6 additions
- Only WhatsApp Business could be exercised on the test phone; the regular WhatsApp path uses the same code with the other package but is verified by host tests only.
- Ads, notification feed/registration and promotions need `--dart-define=WAP_APP_KEY=...` (see `WAPCENTRAL_INTEGRATION_STATUS.md`); without it they are off. Nothing was exercised against the live endpoints with a key.
- The WAP SDKs are path dependencies on `../WAPCentral/sdks/*`; a clone without that sibling folder will not build.
- The first Gradle build with Firebase/AdMob takes ~7 minutes; one build failed once with a duplicate-class-entry error in firebase_core and passed after deleting its build directory.
- Release builds/signing were NOT touched or run (owner instruction). Release/profile artifacts under `build/` pre-date this work.
- MIUI blocks silent USB installs; each install needs the on-device "Install via USB" confirmation.

## Phase 7 additions
- Contact-wise status grouping, contact names and profile photos are not possible with supported access (hash-named files without metadata; contacts live only in WhatsApp's private encrypted database). WazApp groups by day instead.
- A status that exists in WhatsApp but has no file in the status folder cannot be listed; the cause (download timing) was not reproduced end to end and is worded as "may".
- Detection depends on the two `<queries>` package entries; a differently named WhatsApp build (e.g. a cloned/dual app with another package name) is not detected.
- Regular WhatsApp, Android 10-12 and 14+ were not available on the test phone.
