# ADR-006 — Private Folder (hidden + optional device lock, not encryption) and Storage Manager

- **Status:** accepted (Phase 4). Logic verified by host tests; the Android authentication prompt checked on an emulator (see RELEASE_EVIDENCE); not yet on a physical phone; iOS unverified (no Xcode).
- **Context:** The PRD requires a Private Folder with *accurate* security claims, optional device authentication, items kept out of ordinary lists, and a Storage Manager that reports exact usage, flags probable duplicates with explainable rules and never deletes without confirmation. App-private storage plus an authentication gate is **not** encryption.
- **Decision — Private Folder**
  - Moving an item renames its file (and thumbnail) from `library/` to a separate `private/` directory inside the same app-private area and updates the row (`isPrivate`, new paths) — per item, with rollback of the renames if the row update fails, so path and flag can never disagree. Restoring is the reverse. Private rows are excluded from `watchLibrary()`, the Create pickers, search, duplicate detection and the Storage Manager's lists; the Storage Manager shows only an aggregate count/size.
  - Optional lock (default **off**) uses `local_auth` (biometrics or the device PIN/pattern/password). It gates the Private tab and the viewer for private items, and re-locks whenever the app leaves the foreground. **Turning the lock on requires passing the prompt** (no unopenable lock) and **turning it off also requires authentication** (when the device can authenticate). If the lock is on but the phone no longer has a screen lock, the folder opens with an explicit red "Not protected right now" banner instead of locking the user out of their own files.
  - Honest copy everywhere: "Hidden, but not locked" / "Locked with your device authentication"; "files are not encrypted and are deleted if you uninstall WazApp". There is no encryption claim anywhere, and none is implemented (no custom crypto; adding authenticated encryption with Keystore-managed keys is future work with its own migration and tests).
  - Private items cannot be edited (the edited copy would land in the normal library); sharing and "save a copy to gallery" remain explicit user actions.
- **Decision — Storage Manager**
  - Usage is measured from the **file system** (real sizes), not from stored metadata, and reconciled with the directories: unreferenced files, scratch/temp files and entries whose file is missing are shown separately; every byte WazApp keeps is counted once. Only WazApp's own storage is reported - nothing outside it is scanned.
  - Duplicate rules (explained to the user in the UI): (1) **identical** = same kind, same size and same SHA-256 (only files that share a size are hashed, in a background isolate); (2) **look-alike photos** = not identical, same shape (aspect ratio within 2 %) and a 64-bit difference hash (9×8 grayscale) within 4 differing bits. Hashes are cached on the row (schema v2, migrated with `addColumn`). Groups are disjoint with respect to what is suggested for deletion; the suggestion is "keep the oldest", and only on the user's request are extras pre-selected.
  - Deleting always goes through a confirmation that states the number of files and the bytes freed; cleaning unreferenced files re-checks that no row refers to the file and refuses paths outside WazApp's directories.
- **Alternatives rejected:** encrypting with a home-made scheme (unsafe), a separate database for private items (more migration risk), counting private details in the Storage Manager (privacy leak), fuzzy duplicate scoring without an explanation (not explainable), auto-delete of "obvious" duplicates (PRD forbids).
- **Limits:** the lock is a screen gate; rooted devices, backups or file managers with access to the app's data can read the files. Windows test hosts keep file handles open after image decoding, so some UI tests use video rows for delete/rename flows (documented in the tests).
- **Tests:** `private_folder_service_test` (move/restore/rollback), `private_folder_ui_test` (lock states, re-lock on background, settings switch rules, no encryption claim), `storage_service_test` (accounting, duplicates, clean-ups), `storage_screen_test` (confirmations with counts and sizes), `database_migration_test` (v1→v2), `integration_test/device_auth_test.dart` (emulator).
